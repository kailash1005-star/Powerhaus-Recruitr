### What $5 actually buys per cycle

- **~1,250 enriched profiles** ($0.004 each), or
- **~50 searches** — the search actor's **$0.10 minimum per run** dominates. A search returning 3 profiles still costs $0.10, not $0.012.

That minimum is the expensive detail: run budget is consumed by *how many times you search*, far more than by how many profiles come back.

## Two findings that changed the design

### 1. There is no monthly *run-count* cap on this plan

The probe returns no `maxMonthlyActorRuns` field — nothing in `limits` caps the number of runs. The wall is purely **dollars ($5)**.

The planned `APIFY_RUN_WARN_PCT` / `APIFY_RUN_CAP_<actor>` settings were therefore going to guard a ceiling **that does not exist**, and any number chosen for them would have been invented. They are dropped. The threshold is measured against `monthlyUsageUsd / maxMonthlyUsageUsd`.

> The `"free user run limit reached"` message recorded in `SOURCING_FRICTION_ANALYSIS.md` does not map to any field here. Most likely it is either the actor's own per-run item cap (already handled by `APIFY_ENRICH_BATCH=10`) or what Apify returns once the $5 is exhausted. It stays in the classifier's marker list — it is a real observed string — but it is classified as a **spend/plan** block, not a separate run-count ceiling.

### 2. Apify's run history cannot do monthly accounting — `dataRetentionDays: 7`

The billing cycle is **30 days**; run history is purged after **7**. `GET /actor-runs` returned only **4 runs**, all from 2026-07-22.

So Apify's API can never tell us what we spent across a full cycle — only the last week. This is what makes the **local run ledger load-bearing rather than a convenience**: it is the only complete record of our own consumption. Apify supplies the ceiling and the authoritative running total; the ledger supplies the per-actor breakdown and the history that Apify throws away.

### 3. The cycle is not a calendar month

It runs **22nd → 21st**. Any "this month" aggregation using `datetime.now().month` would be wrong for 21 days out of every 30. Cycle boundaries must be read from `monthlyUsageCycle.startAt` / `.endAt`, never computed.

## Wiring these into the alerts

| Signal | Source | Alert at |
|---|---|---|
| Token dead | HTTP 401 on `/users/me` | immediately — **rotate `APIFY_TOKEN`** |
| Spend near cap | `current.monthlyUsageUsd` ÷ `limits.maxMonthlyUsageUsd` | ≥ `APIFY_USAGE_WARN_PCT` (default 80%) — **$4.00 of $5** |
| Spend exhausted | actor refusal strings | immediately — upgrade or wait for the 22nd; **rotating the token will not help** |
| Concurrency | `current.activeActorJobCount` vs 25 | not wired — 4× headroom over our max parallelism |

Field paths verified live, not guessed:
`data.limits.maxMonthlyUsageUsd` · `data.current.monthlyUsageUsd` · `data.monthlyUsageCycle.startAt|endAt`
